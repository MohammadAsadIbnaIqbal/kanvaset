Kanvaset — Real-Time Collaborative Project Workspace
Product & Engineering Specification
Purpose: This document defines the intended product, scope, architecture, features, engineering objectives, and implementation priorities for a portfolio-quality real-time collaborative application. It is intended to be a source of truth for human developers and AI coding agents.
1. Project Objective
Build a focused collaborative workspace/whiteboard where multiple authenticated users can work on the same board simultaneously. Changes made by one user should appear to other connected users in near real time. The project should demonstrate WebSockets, asynchronous backend programming, shared-state management, concurrency, persistence, authorization, and production-oriented engineering.
This is NOT intended to be a full Figma, Miro, or Google Docs clone. The goal is a smaller, well-engineered product whose difficult parts are real-time synchronization and shared state.
2. Product Concept
Users create workspaces and boards. A board contains simple visual objects such as text boxes, sticky notes, rectangles, connectors, and other lightweight elements. Multiple users can open the same board and edit it concurrently.
User signs in.
User creates or opens a workspace.
User creates or opens a board.
User invites another user or shares the board.
Both users open the same board.
Each user can create, move, edit, resize, or delete objects.
Changes are propagated to other connected clients in near real time.
Users can see who else is currently present.
Board state is persisted so it remains available after disconnecting.
3. Primary Engineering Objectives
Implement reliable WebSocket communication between browser clients and a FastAPI backend.
Design a clear shared-state model for collaborative boards.
Handle concurrent edits without corrupting or permanently desynchronizing board state.
Persist board state in PostgreSQL.
Support authentication and board-level authorization.
Use Redis where it provides a clear architectural benefit, especially presence/pub-sub or multi-instance scaling.
Use asynchronous Python/FastAPI patterns appropriately.
Keep real-time transport, persistence, and collaboration logic reasonably separated.
Make the project deployable and demonstrable rather than leaving it as a local prototype.

6. Collaboration Model
Prefer semantic operations/events over repeatedly sending the entire board. For example, moving an object should send an operation such as OBJECT_MOVED rather than serializing the whole board after every mouse event.
OBJECT_CREATED
OBJECT_UPDATED
OBJECT_MOVED
OBJECT_RESIZED
OBJECT_DELETED
USER_JOINED
USER_LEFT
CURSOR_MOVED (polished version)
Operations should contain enough information for validation, authorization, ordering, application, and debugging. Use explicit operation IDs and/or revision numbers.
7. Concurrency and Conflict Handling
This is a central engineering objective. The application must explicitly define what happens when two users modify the same object close together in time.
Do not silently overwrite state without a defined ordering rule.
Validate that the user can modify the board.
Maintain a consistent server-side representation of accepted operations.
Allow clients to recover if they miss an update.
Use operation IDs/version numbers to detect duplicates or stale operations.
For the advanced version, evaluate a CRDT such as Yjs/Automerge if appropriate.
CRDTs are optional for the first version. Do not add CRDT complexity before basic WebSocket synchronization is correct and testable.
8. Real-Time Connection Lifecycle
Client authenticates.
Client opens a WebSocket for a board.
Server authenticates the connection and checks board access.
Server sends the current board snapshot/state.
Client enters presence.
Client sends semantic operations as the user edits.
Server validates and applies accepted operations.
Server broadcasts accepted operations to other authorized clients.
Server persists changes.
On disconnect, the server removes the user from presence.
On reconnect, the client resynchronizes safely.
9. Presence and Live Cursors
Show currently connected users.
Show a name/avatar or identifier for active users.
Show live cursors for other users in the polished version.
Throttle cursor updates to avoid flooding the server.
Treat cursor position as ephemeral state rather than persistent board data.
10. Sharing and Authorization
Every REST request and WebSocket connection must enforce board-level authorization.
Recommended roles:
OWNER — full control
EDITOR — can modify board
VIEWER — can view but not modify
Recommended flow: Owner selects Share → selects a user → chooses a role → access is stored.
11. Conceptual Data Model

WorkspaceMember: workspace, user, role.
Board: id, workspace, name, timestamps, revision metadata.
BoardMember (if board-specific sharing is needed): board, user, role.
BoardObject: id, board, type, position, dimensions, content/properties, timestamps.
Optional BoardOperation: operation ID, board ID, actor, operation type, payload, revision/timestamp.

13. WebSocket Message Design
Use a typed, versionable message envelope. Illustrative example:
{  "type": "OBJECT_MOVED",  "operation_id": "...",  "board_id": "...",  "object_id": "...",  "payload": {"x": 400, "y": 220},  "client_revision": 42}
The exact schema is implementation-dependent, but messages must be typed, validated, traceable, and safe to evolve.
14. Reliability Requirements
Disconnected users must not remain permanently visible as online.
Reconnecting clients must be able to obtain a consistent current state.
Duplicate messages must not create duplicate persistent objects.
Unauthorized users must not receive board data through WebSockets.
Malformed WebSocket messages must be rejected safely.
One client's failure must not terminate other board connections.
Database failures must not be reported as successful operations.
Logs should contain enough context to investigate synchronization problems.

16. Performance Strategy
Do not send the entire board for every small change.
Send semantic operations for edits.
Throttle high-frequency cursor/mouse events.
Batch or debounce appropriate persistence operations.
Use database transactions for state changes that must be atomic.
Use Redis/pub-sub when it solves a real scaling requirement.
Measure WebSocket latency and message throughput.

UPDATED PRODUCT DIRECTION
Kanvaset should allow teams to create projects, organize work into tasks, assign tasks to members, collaborate in real time, see changes immediately, and inspect or restore meaningful previous versions of task/project data.
The product should feel like a focused, technically sophisticated collaborative work-management system—not a generic Jira/Monday/Trello clone and not merely a whiteboard demonstration.
CORE PRODUCT MODEL
Project → Tasks → Collaboration → Activity → Version History
Projects contain members and tasks. Tasks support title, description, status, priority, assignee, due date, tags, timestamps, and comments. Meaningful mutations are synchronized in real time and recorded in history.
UPDATED MVP SCOPE
1. Projects: create/edit projects, manage members, and enforce project-level access.
2. Tasks: create, edit, assign, change status/priority, set due dates, add tags, and comment.
3. Real-time collaboration: task creation, updates, deletion, assignment, status changes, comments where supported, and member/presence changes should propagate through WebSockets without page refreshes.
4. Presence: retain the beta's live-user/presence functionality where available.
5. Version history: maintain an auditable history of meaningful task changes, including revision/version, actor, timestamp, and changed state or structured diff.
6. Version restore: restoring an older version must create a new version; never silently erase history.
7. Activity feed: show important project events such as task creation, assignment, status changes, and priority changes.
8. Authorization: keep server-side permission enforcement. Suggested roles: OWNER, ADMIN, MEMBER, VIEWER.
9. Background work: use the existing Redis/worker infrastructure for real asynchronous needs such as notifications or email; do not add complexity without a use case.
CONCURRENCY AND CONSISTENCY
The server remains the authority for shared state. Prefer entity/field-level mutations over replacing the whole shared board/project state. Use revisions/version checks or optimistic concurrency so stale clients cannot silently overwrite newer state.
Do not introduce CRDTs merely for complexity. Add them only if later requirements genuinely justify them.
EXISTING BETA / CANVAS FUNCTIONALITY
Do not automatically remove the completed collaborative canvas/board functionality. It can remain as a project visualization surface or be gradually adapted into the task workspace. Reuse its working synchronization, WebSocket, presence, authorization, and persistence components.
RECOMMENDED CORE DATA MODEL
User, Project, ProjectMember, Task, TaskComment, TaskVersion, Activity, and optionally Notification.
A separate TaskAssignment table is optional. Use it only if multiple assignees are actually required; otherwise a single assignee relationship is sufficient.
SCOPE BOUNDARY
Do not turn Kanvaset into a full Jira, Monday.com, Asana, or enterprise PM clone. Do not add sprints, Gantt charts, advanced resource planning, time tracking, complex analytics, or large enterprise workflow systems unless explicitly requested later.
UPDATED IMPLEMENTATION ORDER
1. Inspect and understand the completed beta.
2. Preserve working authentication, WebSocket, persistence, authorization, and deployment functionality.
3. Introduce/refine Project and ProjectMember.
4. Introduce/refine Task CRUD and task fields.

6. Connect task mutations to WebSocket events.

10. Strengthen concurrency/revision handling.
11. Add justified notifications/background processing.
12. Test, document, deploy, and polish the portfolio demonstration.

23. Suggested Build Order
Phase 1 — Foundation: Project structure, database, migrations, authentication, workspace/board CRUD.
Phase 2 — Board: Canvas/board UI, object model, create/edit/move/delete objects, REST persistence.
Phase 3 — WebSockets: Authenticated board WebSocket, connection manager, operation messages, broadcasting.
Phase 4 — Synchronization: Initial board snapshot, remote operations, reconnect handling, revisions/operation IDs.
Phase 5 — Presence: Connected users, disconnect handling, live cursors with throttling.
Phase 6 — Concurrency: Define conflict semantics, add tests, improve ordering/idempotency, optionally evaluate CRDTs.
Phase 7 — Production: Redis scaling if needed, logging, monitoring, rate limits, Docker, CI/CD, deployment.
Phase 8 — Portfolio Polish: README, architecture diagram, screenshots, demo video, engineering case study.
